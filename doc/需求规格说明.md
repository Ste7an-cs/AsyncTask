# AsyncTask 软件需求规格说明

## 1. 范围

### 1.1 标识
- 软件名称：AsyncTask（用户态协程异步框架）
- 命名空间：`Coro`
- 版本：见代码仓库提交记录
- 适用对象：基于 Qt / C++17 的异步、IO 密集型应用开发

### 1.2 概述
AsyncTask 基于 `boost::fiber`（有栈协程）提供一套用户态协程异步框架。它将可暂停/恢复的逻辑封装为协程：协程被暂停时**让出所在线程而不阻塞该线程**，调用方可继续执行其它协程，待条件满足后协程被唤醒。目标是使异步代码能像同步代码一样顺序书写，并提供带优先级与线程亲和的协程调度、结构化并发任务编排、以及统一的协程等待接口（信号 / socket / IODevice / future）。软件以头文件与静态库形式随宿主工程编译，依据宿主工程配置（是否含 Qt core / network）自动启用相应能力。

## 3. 需求

### 3.1 能力需求（RX_BASIC_ABILITY）

#### 3.1.1 协程创建与执行（R1_BASIC_ABILITY）

**3.1.1.1 功能需求**
应提供将可调用体作为用户态协程执行的能力，包括：以任务形式创建协程并获取其结果句柄；以低层接口创建带调度属性的协程；在协程内让出/休眠。

**动因（为什么需要协程）**：IO 密集型逻辑若用传统阻塞式 API（如 `waitForXxx`、`future::get`）等待，会**独占并阻塞整个 OS 线程**，等待期间该线程无法处理其它工作；若改用系统线程实现并发，则单个连接/任务一线程的模型在**高并发下线程创建与上下文切换开销巨大**、内存占用高。因此提出以下动因型需求：
- **R1_MOT_1 让出而非阻塞**：协程在等待（休眠、future、IO、信号）时应**让出所在线程而非阻塞它**，使同一线程在等待期间可继续执行其它就绪协程，从根本上消除阻塞式等待对线程的独占。
- **R1_MOT_2 顺序化书写异步逻辑**：应允许将异步等待逻辑以**顺序（同步风格）代码**表达，避免回调/信号槽把一段连续控制流拆散为多处回调（回调地狱），降低异步代码的编写与维护成本。
- **R1_MOT_3 少线程承载高并发**：应支持在**少量工作线程上并发调度大量协程**，以远低于等量 OS 线程的创建、切换与内存开销承载高并发（协程切换在用户态完成、栈按需分配）。

**3.1.1.2 输入输出**
- 输入：一个可调用体（函数或 lambda），以及可选的优先级、线程亲和、名称。
- 输出：一个任务对象，使用方可据以取回执行结果。

**3.1.1.3 行为过程描述**
- 创建任务：使用方把一个可调用体交给框架，即刻得到任务对象；该可调用体在协程中运行，创建方不被阻塞、可继续做别的事——解决“发起一段异步工作后必须原地等着”的问题。
- 获取结果：使用方通过任务对象取回返回值或错误；结果未就绪时的等待是**协程让出线程**式的，不阻塞线程，等待期间同线程其它协程仍能推进。
- 让出/休眠：使用方可在协程内主动休眠或让步，把线程交还调度器，从而用少量线程承载大量协程。

**3.1.1.4 行为参数**
- 优先级：低 / 普通 / 高（默认普通）。
- 线程亲和：共享（任意线程）/ 粘附（首次执行线程）/ 固定（指定线程），默认绑定到创建时所在线程。
- 异常：可调用体抛出的异常在协程边界被捕获并转为错误结果（见 R4），不跨协程传播。

#### 3.1.2 优先级与线程亲和调度（R2_BASIC_ABILITY）

**3.1.2.1 功能需求**
应提供在少量工作线程上调度大量协程的能力，支持三级优先级与三种线程亲和，并支持跨线程工作分发。

**动因（为什么需要协程调度）**：要解决的问题是“如何在**不为每个任务开一个 OS 线程**的前提下承载高并发，同时兼顾任务的轻重缓急与线程隔离约束”。方案是引入用户态协程调度：把大量协程复用到少量工作线程上，用**优先级**表达轻重缓急、用**线程亲和**表达“某些协程必须（或不必）固定在特定线程”的约束（例如 Qt 对象须在其所属线程访问），并允许无归属的协程在空闲线程间分发以提高吞吐。

**3.1.2.2 输入输出**
- 输入：使用方在创建协程时指定的优先级与线程亲和。
- 输出：协程在满足亲和约束的线程上、按优先级被取用执行。

**3.1.2.3 行为过程描述**
- 就绪协程按线程亲和归类、按优先级排序，纳入一个跨线程共享的就绪集合。
- 各工作线程从中挑选**满足自身亲和约束、优先级最高**的协程执行；固定/粘附协程只被目标线程取走，共享协程可被任意空闲工作线程取走。
- 框架内置一个工作线程池（线程数默认按 CPU 核数确定）承接协程执行。
- 在当前无法调度协程的线程（如主线程正阻塞于等待）上创建的共享协程，可由其它工作线程取走执行，从而不被“卡住的线程”拖住。

**3.1.2.4 行为参数**
- 亲和语义：共享=任意可用线程；粘附=绑定到首次执行它的线程；固定=绑定到指定线程。
- 优先级：同一线程内高优先于普通、普通优先于低。
- 限制：**运行期反复更改线程亲和（迁移线程）不受支持**（见 3.6 R1_OTHER），线程归属应在创建时确定。

#### 3.1.3 结构化并发（R3_BASIC_ABILITY）

**3.1.3.1 功能需求**
应提供任务链式编排能力：后继任务、结束回调、取消、结果获取。

**动因（为什么需要结构化并发）**：并发任务若各自为战，容易出现“谁等谁、谁负责收尾、如何整体取消”无人管辖的问题，错误与资源释放难以追踪。方案是把有依赖关系的协程组织为一条**任务链**：后继在前驱完成后自动以其结果启动（顺序表达依赖，取代手写状态同步），结束回调在整链结束时统一触发（集中收尾），一处取消即让后续协程短路（整体可取消）。

**3.1.3.2 输入输出**
- 输入：一个已有任务、后继函数、结束回调（按操作而定）。
- 输出：后继任务对象；可取回最终结果。

**3.1.3.3 行为过程描述**
- 后继任务：在前一个任务**完成后**，自动以其结果为入参启动下一个任务；后继默认沿用前驱的优先级与线程模型，使用方以链式书写依赖关系，无需手写同步。
- 结束回调：登记的收尾回调在**整条任务链全部结束时**统一触发，可登记多个，便于集中释放资源。
- 取消：对任务链发起取消后，尚未开始的后续任务在启动前即短路、返回中断结果。
- 取结果：取回任务结果；结果未就绪时以**协程让出线程**的方式等待，不阻塞线程。

**3.1.3.4 行为参数**
- 前驱出错或任务链已被取消时，后续任务返回“中断”结果。
- 结束回调在任务链最后一个节点完成时触发。

#### 3.1.4 结果与错误传递（R4_BASIC_ABILITY）

**3.1.4.1 功能需求**
应提供承载“值或错误”的结果类型，支持 `void` 与携带错误码，禁止异常跨协程传播。

**动因（为什么不跨协程抛异常）**：协程在不同线程上被调度、可被取消或超时，若让异常跨越协程边界传播，将破坏结构化并发的确定性、难以在正确线程被捕获。方案是统一以**结果对象**承载“成功值”或“错误码”：协程内的异常在边界被就地转为错误码结果，调用方以统一方式判断成功/失败，取消、超时、通道关闭等也表达为错误码而非异常。

**3.1.4.2 输入输出**
- 输入：一个成功值，或一个错误码。
- 输出：结果对象，使用方可查询是否成功、取值、取错误、或带默认值取值。

**3.1.4.3 行为过程描述**
结果对象承载“成功值”或“错误”二选一：使用方先判断是否成功，成功则取值、失败则取错误码，也可在失败时取一个默认值；支持没有返回值（`void`）的场景，并能作为协程返回值与等待结果统一使用。

**3.1.4.4 行为参数**
- 结果为“失败”时，取值操作的返回不可用，应改取错误。
- 取消、超时、来源关闭、内部异常等都表达为相应错误码，而非抛出异常。

#### 3.1.5 统一协程等待（R5_BASIC_ABILITY）

**3.1.5.1 功能需求**
应提供统一的协程等待载体与工厂：单一重载入口 `coro(...)` 返回等待器 `Awaitable<T>` 或对象包装器；统一的消费函数 `await` / `generate`；等待器与具体来源（Qt/std）解耦。

**动因（为什么需要协程化等待）**：Qt 的异步来源（信号、socket 就绪、`QFuture` 完成）原生只能经**信号槽回调**获取，一段“连接→读→处理→再读”的逻辑被拆散到多个槽函数中，状态需在成员变量间传递、控制流难以跟踪；而 Qt 自带的 `waitForReadyRead` 等同步等待又会**阻塞事件循环所在线程**。协程化等待正是为消除这一矛盾。因此提出以下动因型需求：
- **R5_MOT_1 回调转顺序等待**：应把信号/IO/future 等回调式来源统一封装为可 `await` 的等待器，使调用方以 `auto r = await(coro(obj,&sig));` 的**顺序写法**取得结果，避免为每个异步来源编写独立槽函数与散落的状态机。
- **R5_MOT_2 等待不阻塞事件循环**：等待器的 `await` 应在无数据时**让出协程**而非阻塞线程，使等待期间 Qt 事件循环与其它协程仍能推进，取代 `waitForXxx` 之类独占线程的同步等待。
- **R5_MOT_3 流式消费**：应支持将持续产生的异步事件（连续到达的数据、反复触发的信号）以 `generate(a)` **像迭代容器一样顺序消费**，替代“信号触发一次进一次槽”的离散回调模型。

**3.1.5.2 输入输出**
- 输入：一个异步来源——Qt 信号、Qt 的 IO/socket/服务器对象，或标准库/Qt 的 future。
- 输出：一个等待器（或包装器，其方法返回等待器）；消费后得到一次结果，或一个可迭代的数据流。

**3.1.5.3 行为过程描述**
- 建立等待器：使用方以统一入口 `coro(来源)` 把某个异步来源包装成等待器；对 socket/IO/服务器等，包装器的方法名沿用原 Qt 命名（如接收数据、等待连接、接受新连接），使用方无需学习新名字。
- 顺序取用：使用方用 `await` 顺序取回一次结果，等待期间协程让出线程；也可带超时取用。
- 流式取用：对会持续产生的来源（不断到达的数据、反复触发的信号），使用方用 `generate` **像遍历容器一样**逐个取用，取代“每触发一次进一次回调”的写法。
- 自动收尾：来源对象销毁或应用退出时，等待器自动关闭，使正在等待/遍历的协程自然收敛；等待器可跨线程安全传递，且不绑定具体来源类型。

**3.1.5.4 行为参数**
- 信号无参→得到空结果；单参→得到该值；多参→得到一组参数（元组）。
- 超时取用未在时限内到达数据时返回“超时”结果；来源已关闭时返回“无数据”结果，使循环自然结束。
- 接收数据类操作在建立时若已有缓冲数据会立即投递，避免“先检查后等待”造成的漏读。
- 使用方在协程执行期间等待某对象析构时需注意：其析构可能延后（见 3.6 R2_OTHER）。

#### 3.1.6 Qt 集成与安全退出（R6_BASIC_ABILITY）

**3.1.6.1 功能需求**
应提供与 Qt 事件循环共存的调度器、协程线程、应用集成与安全退出能力。

**动因（为什么需要与 Qt 共存的特殊处理）**：Qt 应用天然由 `QCoreApplication::exec()` 的事件循环驱动，而协程调度也需要一个循环来推动；二者在同一线程若各跑各的会互相独占，导致“要么事件不处理、要么协程不调度”。方案是让协程调度器成为主循环，并在其空闲时**代为驱动 Qt 事件**，使同一线程内二者共存；同时提供安全退出流程，避免协程活过 Qt 应用对象而访问已销毁的事件系统造成崩溃/卡死。

**3.1.6.2 输入输出**
- 输入：`installFiberApplication()`、`Coro::exec()`、`Coro::quit()`。
- 输出：主线程/工作线程可同时调度协程与处理 Qt 事件；退出时干净收尾。

**3.1.6.3 行为过程描述**
- 事件共存：协程调度器在自身空闲（无就绪协程）时代为泵送一轮 Qt 事件，使协程调度与 Qt 事件循环共存于同一线程，互不独占。
- 应用集成：`installFiberApplication()` 在主线程安装支持协程的调度器并启动工作线程池；`Coro::exec()` 让主线程留在协程调度器中（协程与 Qt 事件都能推进）；另提供支持协程的工作线程（QThread）以承载需固定线程的协程。
- 安全退出：`Coro::quit()` 先唤醒所有正挂起等待的协程使其收尾，再排空在途协程与事件，最后停线程池并退出——确保协程在 Qt 应用对象销毁前收敛，避免退出期崩溃/卡死。

**3.1.6.4 行为参数**
- 主循环必须用 `Coro::exec()` 驱动，**不得用 `QCoreApplication::exec()`**（二者在同一线程互斥）。
- 协程调度期间 `deleteLater` 的对象一般要到退出排空时才真正析构（见 3.6 R2_OTHER）。

### 3.2 外部接口需求（rx_interface）

#### 3.2.1 接口标识和接口图
外部接口以 C++ 头文件形式提供，宿主工程通过 `include(AsyncTask.pri)` 引入。主要公开接口分组：

```
task 层:   makeTask() / FiberTask<T>::{then,on_finally,cancel,get}
           installFiberApplication() / Coro::exec() / Coro::quit()
await 层:  coro(...) / await(a[,timeout]) / generate(a)
           Awaitable<T> / Generator<T>
基础:      Result<T,E> / Coro::sleep|msleep / launch_properties()
```

#### 3.2.2 任务与应用接口（R1_INTERFACE）
- `makeTask(fn, pri=Normal, affine=fixed(当前线程)) -> FiberTask<T>`
- `FiberTask<T>::then(fn[,pri,affine]) / on_finally(cb) / cancel() / get() -> Result<T>`
- `installFiberApplication()` / `int Coro::exec()` / `Coro::quit()`

#### 3.2.3 等待接口（R2_INTERFACE）
- `coro(obj,&sig)` / `coro<Types...>(obj,&sig)` -> `Awaitable<...>`
- `coro(QIODevice*/QAbstractSocket*/QTcpServer*/QLocalSocket*)` -> 对应包装器（方法返回 `Awaitable`）
- `coro(std::future<T>&&) / coro(const QFuture<T>&)` -> `Awaitable<T>`
- `await(a) / await(a, timeout) -> Result<T>`；`generate(a) -> Generator<T>`
- 头文件：伞头 `await/coro.hpp` 一次性引入；亦可按需单独引入 `corosignal/corofuture/coroiodevice/corosocket/corotcpserver/corolocalsocket.hpp`。

#### 3.2.4 基础接口（R3_INTERFACE）
- `Result<T,E>`：`has_value()/value()/error()/value_or()`
- `Awaitable<T>`：`channel()/setOnClose(fn)/await()/await_for(timeout)/resolve(v)/close()`
- `Generator<T>`：`begin()/end()/next()/close()`
- `Coro::sleep(s)/msleep(ms)`、`launch_properties(fn,pri,affine,name)`

### 3.3 内部接口需求（rx_in_interface）

以下为框架内部各模块间的职责契约，不对使用方开放；具体形式见设计文档（`doc/软件设计说明.md`、`doc/架构设计.md`）。

- **R1_IN_INTERFACE 调度算法**：框架须向底层协程库提供一套调度算法，决定协程何时就绪、下一个运行哪个、无就绪协程时如何驱动 Qt 事件，并遵守底层协程库对上下文管理的约定。
- **R2_IN_INTERFACE 就绪队列存取**：调度算法须能对内部的“就绪协程集合”进行入队、按线程亲和取出、按需移除等操作；跨线程访问须串行化以保证一致。
- **R3_IN_INTERFACE 线程挂起/唤醒**：须提供“挂起线程但允许其继续调度协程”的机制，供线程池与协程线程在需要时挂起、在退出时唤醒。

### 3.4 内部数据需求（rx_in_data）

以下为框架内部维护的数据，不对使用方开放；结构细节见设计文档。

- **R1_IN_DATA 数据队列**：跨线程、跨协程安全的数据队列，支持投递、取出、限时取出与关闭；作为等待器传递数据的底层载体。
- **R2_IN_DATA 就绪协程集合**：保存就绪协程，按线程亲和分组、组内按优先级排序，供调度按约束取用；并发访问须串行化。
- **R3_IN_DATA 任务链状态**：任务链各节点共享的状态，含在途节点计数、取消标志、结束回调列表。
- **R4_IN_DATA 协程调度属性**：每个协程携带的优先级、线程亲和与名称。
- 数据一致性：上述并发数据须受相应保护；协程的线程亲和应在创建时确定、运行期不迁移。

### 3.5 设计和实现约束（rx_design）

- **R1_DESIGN 语言/标准**：C++17（`gcc ≥ 9.0`）。
- **R2_DESIGN 依赖**：Boost ≥ 1.89.0（fiber/context/thread/chrono，静态链接，`/usr/local`）；Qt ≥ 5.12（可选）。
- **R3_DESIGN 构建**：qmake；`include(AsyncTask.pri)`；依据宿主工程 `QT` 配置（core/network）自动启用 Qt 调度器与信号/socket 等待能力。
- **R4_DESIGN 体系结构**：四层（detail / executor+scheduler / task / await），基于 boost.fiber 有栈协程；自定义调度算法实现优先级+线程亲和+跨线程分发。
- **R5_DESIGN 解耦与可扩展**：等待器本体不含任何 Qt 类型，Qt 依赖集中在 `coro()` 工厂一侧，并按来源类型拆分头文件，支持按需引入与将来扩展非 Qt 来源。
- **R6_DESIGN 主循环模型**：必须以 `Coro::exec()` 作为主循环、由调度器在空闲时驱动 Qt 事件；不得以 `QCoreApplication::exec()` 驱动。
- **R7_DESIGN 平台**：主要支持 Linux（x86_64）。

### 3.6 其他需求（rx_other）

- **R1_OTHER 已知限制—运行时改亲和**：不支持在运行期反复更改线程亲和以迁移协程所在线程；高并发下会命中底层协程库跨线程迁移的时序缺陷，不保证迁移正确。线程归属应在协程创建时确定。
- **R2_OTHER 已知限制—调度期 deleteLater**：协程调度期间用 `deleteLater` 标记的对象通常要到 `Coro::quit()` 排空时才真正析构；若需在协程执行期确定性地释放对象，应改用直接 `delete` 或另行处理。
- **R3_OTHER 交付物**：boost 1.89 源码包因体积未随仓库提供，需按 REF-1 自行下载编译安装到 `/usr/local`。
- **R4_OTHER 测试**：随仓库提供 5 套 QtTest 用例（testfibertask/testexecutor/test_scheduler/testfiberawait/testProfile）；测试 `.pro` 使用 `-static-libasan`（不与动态 `-lasan` 混用）。testProfile 为长时间压力测试，会超时属预期。

## 4. 注释

### 4.1 术语与缩写
| 缩写/术语 | 含义 |
|---|---|
| 协程 / fiber | 有栈用户态协程，暂停时让出线程、不阻塞线程 |
| Awaitable | 协程等待/数据载体，消费方 `await` 取值 |
| Generator | 把 Awaitable 当数据流迭代 |
| Affinity | 线程亲和：Shared/Sticky/FixedId |
| Priority | 优先级：Low/Normal/High |
| SRS | 软件需求规格说明（本文档） |

### 4.2 需求标识说明
- `RX_BASIC_ABILITY`：能力需求（X 为序号，如 R1_BASIC_ABILITY）。
- `Rx_MOT_y`：动因型需求，说明该能力“为什么需要用协程解决”（x 对应能力序号，如 R1_MOT_1）。
- `rx_interface` / `rx_in_interface` / `rx_in_data` / `rx_design` / `rx_other`：分别为外部接口、内部接口、内部数据、设计约束、其他需求；具体条目以 `R<n>_INTERFACE` 等标识。

本文档为正式需求规格说明，与概述性的 `doc/需求文档.md` 并存；实现细节与图示分别见 `doc/架构设计.md`、`doc/类图与时序图.md`。
